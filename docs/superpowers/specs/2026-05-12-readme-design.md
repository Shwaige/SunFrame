# README 重写设计

## 背景

当前项目已经从单文件脚本演进为一个包含多个命令和模块的自动化工具。现有 `README.md` 有以下问题：

- 启动命令和实际代码中的命令不完全对齐
- 使用说明、维护说明、排错信息混在一起，结构不稳定
- 新增的 `activity`、`daily-self`、缓存刷新、好友回扫等行为没有被系统性说明
- 部分示例命令和真实行为不一致，容易误导使用者

目标读者是“会用命令行的少量同事/朋友”，因此 README 既要让人快速运行，也要能解释核心机制和常见故障。

## 目标

重写 `README.md`，使其成为一份分层维护手册，满足以下目标：

1. 让使用者可以快速找到最常用命令并直接复制运行
2. 让维护者明确每个命令和模块的职责边界
3. 解释缓存、登录刷新、活动处理、好友扫描等关键机制
4. 提供最常见故障的排查入口
5. 保持 README 聚焦“使用与维护”，不下沉到函数级实现细节

## 非目标

本次不做以下事情：

- 不修改业务代码逻辑
- 不为每个函数补开发注释
- 不把 README 扩写成完整 API/架构文档
- 不新增图片、流程图或额外文档站点

## 推荐方案

采用“分层维护手册”结构：

### 1. 快速开始

放最常用命令，优先展示批量模式和单账号模式：

- `daily`
- `daily-self`
- `self-op`
- `sign`

设计原则：

- 命令可直接复制
- 批量和单账号各给最小示例
- 不在这一节解释内部逻辑

### 2. 账号配置

说明两种凭证来源：

- 直接 `openId/sid`
- `YGMC_LOGIN_ACCOUNT / YGMC_LOGIN_PASSWORD`

并说明：

- 默认优先读取 `.ygmc_cache.json`
- 缓存异常时会自动刷新凭证
- 缓存文件不会进入 git

### 3. 批量文件格式

集中说明当前代码真实支持的格式：

- `label,login_account,login_password,login`
- `label_prefix,login_prefix,start,end,password,login_range`

并指向：

- `accounts.batch.txt`
- `accounts.example.txt`

### 4. 命令总览

命令必须与 `ygmc/cli.py` 实际保持一致，按“两层结构”组织：

常用命令：

- `daily`
- `daily-self`
- `self-op`

单模块命令：

- `sign`
- `activity`
- `status`
- `friends-op`

每个命令只解释：

- 做什么
- 不做什么
- 适合何时使用

### 5. 模块行为说明

说明实际行为，而不是泛泛命名：

- `sign`：签到、累签奖励、月累签奖励
- `activity`：新人红包、母亲节活动（固定入口）
- `self-op`：自己农场/畜牧场的一键与单次回退
- `friends-op`：好友农场/畜牧场，多分页、多轮回扫

### 6. 输出说明

解释终端里的关键输出：

- `凭证来源`
- `农场链接`
- `今日签到状态`
- `自己操作数量 / 跳过数量 / 失败数量`
- `农场好友处理数量`
- `畜牧场=未开通，已跳过`

目标是让使用者看到输出时知道含义，不需要去读代码。

### 7. 常见问题

优先写真实遇到过的问题：

- `Connection refused`
- 缓存凭证失效
- 自己畜牧场未开通时的行为
- 好友为什么“还有没扫完”
- `git push` 非 fast-forward

每个问题控制在 2-5 行，先给结论，再给处理方式。

### 8. 代码结构

只列模块职责，不扩成内部实现文档：

- `ygmc/cli.py`
- `ygmc/sign.py`
- `ygmc/activity.py`
- `ygmc/self_ops.py`
- `ygmc/friends_ops.py`
- `ygmc/session.py`

### 9. 注意事项

集中放项目级约束：

- 不要提交真实 `sid/openId`
- `.ygmc_cache.json` 不入库
- 活动逻辑可能是临时性的
- 请求间隔可通过 `YGMC_REQUEST_INTERVAL` 调整

## 可选方案对比

### 方案 A：极简操作手册

优点：

- 短
- 好复制

缺点：

- 无法解释缓存、活动、好友回扫等行为
- 维护者仍要读代码

### 方案 B：分层维护手册（推荐）

优点：

- 兼顾使用和维护
- 与项目当前复杂度匹配
- 不会膨胀成开发设计文档

缺点：

- 比极简版更长
- 需要定期随命令更新

### 方案 C：开发文档型 README

优点：

- 最全

缺点：

- 维护成本高
- README 过重
- 与目标读者不匹配

## 推荐结论

采用方案 B。

原因：

- 目标读者不是完全新手，也不是只看源码的开发者
- 项目已经具备多命令、多模块、多分支逻辑，极简 README 不足以支撑维护
- 但又没有必要把 README 扩成完整架构文档

## 实施范围

本次 README 重写将：

- 重组现有内容结构
- 删除失真或过时命令
- 补充当前命令与真实行为说明
- 增加常见问题与排错章节

本次不会：

- 改 CLI 接口名
- 改命令输出格式
- 增加新的业务功能
